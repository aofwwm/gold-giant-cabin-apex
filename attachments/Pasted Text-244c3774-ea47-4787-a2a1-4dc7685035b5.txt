Please change Kairos Dating invitations to a NO-LOGIN two-link architecture.

IMPORTANT:

I do NOT want planner accounts or login.

Current Dating invitation flow already supports:

- creating an invitation
- public recipient link
- recipient viewing invitation
- recipient replying:
  “I’m up for it”
  “Suggest another time”
- response saved to Supabase

CURRENT PROBLEM:

The original planner has no persistent identity, so Kairos does not reliably know which invitation/reply belongs to the planner.

I have added this column to:

public.dating_invitations

planner_token text

with a unique index.

Implement a TWO-TOKEN invitation system.

==================================================
ARCHITECTURE
==================================================

Every new Dating invitation must have TWO separate secure random tokens:

1. RECIPIENT TOKEN

Stored as:

invite_slug

Used for:

/date/:inviteSlug

This is the link sent to the other person.

Example:

https://<domain>/date/A7kP9xLmQ2Rt


2. PLANNER TOKEN

Stored as:

planner_token

Used for:

/date/manage/:plannerToken

Example:

https://<domain>/date/manage/Q8mP2xL9KaRt

This link is PRIVATE and belongs to the planner.

==================================================
SECURITY
==================================================

Both tokens must be:

- cryptographically random
- 12–16 characters
- URL-safe
- alphanumeric only
- non-sequential
- difficult to guess

Example:

A7kP9xLmQ2Rt

Do NOT use:

1234
date1
sequential IDs

Do NOT make the short display code the security mechanism.

==================================================
INVITATION CREATION
==================================================

Update the existing create_dating_invitation flow.

When planner creates an invitation:

Generate:

invite_slug

AND:

planner_token

Store both in:

public.dating_invitations

Existing RLS must remain enabled.

Continue using the controlled RPC / SECURITY DEFINER architecture.

Do NOT revert to anonymous direct INSERT.

==================================================
CREATE RPC
==================================================

Update:

public.create_dating_invitation

so it stores planner_token.

The successful response should return:

{
  invite_slug,
  planner_token,
  status
}

Do not expose planner_token through the public recipient retrieval RPC.

==================================================
AFTER CREATION
==================================================

Kairos should generate TWO URLs:

recipientUrl:

https://<domain>/date/<inviteSlug>

plannerUrl:

https://<domain>/date/manage/<plannerToken>

==================================================
SHARING
==================================================

WhatsApp
Share
Copy Link
Copy Message + Link

must ONLY share:

recipientUrl

NEVER share plannerUrl.

==================================================
PLANNER LINK
==================================================

After creating the invitation, show a small private section to the planner:

YOUR PRIVATE PLANNER LINK

Keep this link private. It lets you see their reply later.

[ Copy planner link ]

Do not make this overly prominent.

==================================================
SAVE PLANNER TOKEN LOCALLY
==================================================

For convenience, store the planner token locally in the planner's browser.

Associate it with the current Dating plan.

Example concept:

kairosDatingPlannerTokens[datingPlanId] = plannerToken

Use localStorage or the existing persistent client storage architecture.

This is for convenience only.

The actual authority is the secure planner_token stored in Supabase.

==================================================
NO LOGIN
==================================================

The planner must NOT need:

- email
- password
- Google login
- Supabase Auth account

The private planner token acts as possession-based access.

==================================================
PLANNER MANAGEMENT ROUTE
==================================================

Create:

/date/manage/:plannerToken

This page should show:

DATE INVITATION

Invitation details

Share again

Copy recipient link

Revoke invitation

Optional:
Edit/replan

==================================================
PLANNER STATUS RPC
==================================================

Create a controlled RPC:

public.get_dating_invitation_for_planner(
  p_planner_token text
)

Use SECURITY DEFINER.

It should return ONLY the invitation matching that exact planner token.

Return fields such as:

invite_slug
title
date/time information
status
recipient_note
visibility
public_payload
created_at
updated_at

Do NOT return:

planner_token

unless technically required.

Do NOT return other users' invitations.

Refresh planner status when:
